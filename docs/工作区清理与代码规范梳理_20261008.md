### 4.7 注释与命名规范现状（正面评价）

本项目在单文件无类型系统的前提下，靠**注释纪律**弥补了很大一部分可维护性风险：

- **400 处 `// vX.Y.Z：` 版本注解** —— 每一处改动可追溯到版本，这是它区别于普通"大泥球"的关键；
- **79 处 `❗` 标记** —— 直接标注踩坑原因与后果，而非只描述「做了什么」；
- **1,064 行注释 / 7,085 行 setup ≈ 15% 注释率**，且大量是"为什么"而非"是什么"；
- `return{}` 与 `__foodin` 块本身带历史事故注释（11306-11309 记录 `saveData/showToast` 漏导出的 P0）；
- 命名：`camelCase` 变量/函数、`SCREAMING_SNAKE` 常量、`fi-` 前缀组件类 —— 全文件未见破坏性命名。

**结论：命名与注释规范执行度高，本项目的真实风险不在"写得乱"，而在"单文件 + 手写白名单 + 双写盘路径"这三条结构性约束。**

### 10.1 ① P0 — `loadData` 逐键隔离 + 损坏隔离

**旧实现的致命路径**：4 个 `JSON.parse` 共用一个 `try/catch` → `products` 一旦损坏就整段跳到 catch → `records` / `settings` / `barcodeCache` **全都不加载**（保持空值）→ 随后任一次 `saveData()` 把空值写回盘 = **一次坏数据永久丢失**。

- 有键损坏时 `toastErr('读取本地数据','部分数据损坏，已隔离备份')`（21 字，符合 toast ≤22 字规则）

| **P1 · 自愈移出启动早期** | `dedupeProductIds()` 原在 `initSyncEngine()` **之前**（baseState 为 null → 只能直写 localStorage，**新 id 永远上不了云**）。移到其后、`purgeGhostProducts()` 之前；落盘改为「baseState 就绪 → `saveData()`（事件流）；否则沿用直写」，两者兼得 |
| **P1 · 顺带修一处自相矛盾** | `tourDone` 补写在 baseState 就绪前就调 `saveData()` → 会把**全部商品**当新增整包推上云（与本文件内 v2.33.0 的注释相矛盾）。改为 `pendingBootSave` 延迟到 `initSyncEngine()` 之后 |
| **P0 · 导入不再静默丢商品** | 导入区分两种情况：①同一商品（名称+条码都同）→ 仍按 `updatedAt` 合并；②**只是 id 撞车** → 两条都保留、给来件分配确定性 id、并把属于它的流水按名称改挂。另：不再用 Map 承载输出（会把「本地已有的同 id 商品」折叠掉） |
| **可测性** | 从 `importData` 抽出 `applyImportPayload`（导入入口是「数据整理」折叠区里的隐藏 file input，自动化驱动不了），登记进 `window.__foodin` |
| ❌ **取消** | P2 一键拆分入口 / 预览 / 撤销 —— 不做 UI |

### 11.2 ❗更正自己的一处误判

设计初稿 §12.1 把 `applyLegacyUnion` 的 seen-map 判为 bug，并称「2 行可修」。**复核后确认是误判**：
该循环的语义是「本地已有该 id → 跳过来件；**云端数组内部的同 id 条目照收**」——这是**保数据**行为。按初稿去「修」成 `pmap.set(...)`，效果是**静默丢掉云端第二条**，用数据丢失换掉重复，更糟。
真正该做的是用**确定性引擎**把它们拆成两条合法商品（本来就是自动自愈在做的事）。设计文档 §12.1 已改写为更正说明。
> 顺带复核确认：`replayState` 用 `new Map(...)` 以 id 收敛（10618）→ **事件重放不可能产生重复 id**。
