# FoodIn 云同步深度分析与改造方案

> 基于 v2.17.2 代码全量走查（index.html 3196-3211 / 4252-4681 / 4712-4744）。
> 本文只做分析与方案，不改动代码；确认后再实施。

---

## 一、现有同步实现：关键代码路径

### 1.1 架构总览（v2.17.0 事件日志引擎）

```
本地操作（录入/入库/编辑/删除/撤销/拖拽）
   │
   ▼
saveData()  [L3196]
   ├─ 写 localStorage（products / records / settings / barcodeCache）
   ├─ diffToEvents()  [L4319]  当前状态 vs baseState 差分 → 事件追加到 pendingEvents 并落盘
   └─ 15 秒防抖 → cloudSync(false)
                      │
                      ▼
cloudSync()  [L4488]  ──────────── jsonbin.io 单 Bin ────────────
   1) fetchCloudRecord()  GET /latest（v3 gzip 自动解压）          [L4440]
   2) 推进 lastSeenTs 水位 → diffToEvents() 差分入队
   3) 反误删守卫：本地有、重放无、云端不认识 → 补 upsert（防清空云端）  [L4522]
   4) replayState(快照 + 云端事件 + 本地待推) → 写回本地               [L4369]
   5) 条码缓存并集（updatedAt 取新）
   6) 需要推送时：事件折叠（>30 保留最近 20，其余折叠进快照+knownIds） [L4589]
      → gzip v3 压缩 → PUT 全量覆盖
   7) 回读「尾事件确认」→ 确认才清空 pendingEvents                    [L4622]

其他入口：
   - 启动时：有待推事件 或 距上次同步 ≥10 分钟 → cloudSync()          [L4725]
   - 定时自动保存：autoSaveInterval 分钟间隔 → cloudSync()           [L4186]
   - 手动：主页「云同步」按钮 / 设置页「立即同步」
```

### 1.2 设计上的正确决策（保留）

这些是符合业界做法的，**不要推倒重来**：

| 决策 | 对应业界实践 |
|---|---|
| 事件只增不改、删除用显式墓碑、不靠"缺席推断" | CouchDB tombstone / Event Sourcing |
| 字段级 patch 合并（不同设备改不同字段互不覆盖） | LWW-Register（字段粒度） |
| Lamport 时钟（ts 不早于已见事件）+ (ts, id) 全序 | Hybrid Logical Clock 的简化版 |
| 事件先落盘再防抖上云（刷新/断网不丢变更） | Outbox 模式 |
| 拉取失败绝不推送；推送后回读验证 | 乐观锁 / read-your-write 校验 |
| 快照 + 水位折叠控制体积；gzip 突破 100KB 上限 | 事件溯源标准快照机制 |

**结论：引擎骨架是对的。问题集中在 4 个实现级 bug + 1 个语义缺陷 + 1 个传输层天花板。**

## 二、根因分析：为什么同步问题"修不完"

### 根因 1（P0・正确性 bug）：二次折叠会丢掉上一版快照的全部内容 → 静默数据丢失

**位置**：`cloudSync()` L4589-4611

```js
const allMap = new Map();
for (const e of dedupedCloud) allMap.set(e.id, e);   // ← 只有云端"保留的"事件
for (const e of syncState.pendingEvents) allMap.set(e.id, e);
const allEvents = [...allMap.values()].sort(eventOrder);
if (allEvents.length > 30) {
  const dropped = allEvents.slice(0, allEvents.length - 20);
  const dropState = replayState(null, dropped, []);  // ← 从空状态重放，旧快照被丢弃！
  snapshot = { products: dropState.products, ..., knownIds };
```

**问题链条**：
1. 第一次折叠后，云端 `events` 只剩最近 20 条，更早的数据全部在 `snapshot` 里。
2. 第二次折叠时，`allEvents` = 云端保留的 20 条 + 本地待推，**不含旧快照**。
3. `replayState(null, dropped, [])` 从空状态重放 → 新快照里**所有早已被折叠、近期没动过的商品/记录全部消失**。
4. 其他设备同步后重放 → 这些商品本地也被删掉。

**触发条件**：家庭正常使用每天产生几条~十几条事件，第一次折叠（30 条）后，再攒 10 条左右就触发第二次折叠。**这是"商品莫名其妙消失/时有时无"的最可能元凶。**

**为什么难查**：折叠只在推送路径触发、依赖事件累计量，复现需要跨多次同步，单设备单次测试完全正常（_test_sync_v217.js 的场景都停在第一次折叠）。

### 根因 2（P0・正确性 bug）：`knownIds` 不跨折叠累积 → 删除墓碑失效 → 僵尸商品复活

**位置**：L4600-4606

```js
const knownIds = [];
for (const e of dropped) { ... knownIds.push(k); }   // ← 只记录本次折叠的 key
snapshot = { ..., knownIds };                         // ← 旧快照的 knownIds 被整体替换
```

v2.17.2 引入 knownIds 是对的（被折叠的删除墓碑必须留痕，否则残留设备把已删商品误判为"本地新增"而复活）。但**每次折叠都从零重建 knownIds**，上一版快照里累积的墓碑全部作废。

**后果**：一台几周没开机的家庭成员手机（常见场景！）重新打开时，它本地还存着早被删除的商品 → 云端墓碑已随旧 knownIds 丢失 → 反误删守卫反而帮倒忙，把僵尸商品 upsert 回云端，**扩散到全家设备**。

### 根因 3（P0・正确性 bug）：重放顺序违反全序 → 并发"清空/删除"被旧编辑覆盖

**位置**：`replayState()` L4390-4391

```js
eventsAfter(cloudEvents, snapshot && snapshot.upToId).sort(eventOrder).forEach(apply);
(pendingEvents || []).slice().sort(eventOrder).forEach(apply);  // ← 本地待推无条件最后应用
```

本地待推事件**不管 ts 早晚，永远最后生效**。场景：

- 设备 B 离线期间编辑了商品 X（事件 ts 较早，未推送）；
- 设备 A 清空全部数据 / 删除 X（删除事件 ts 较晚，已上云）；
- B 同步时：重放先应用 A 的删除，再应用 B 的旧 upsert → **X 复活**，清空白做。

 Lamport 全序的意义就是"全系统一个顺序"，分段应用等于自己破坏了这个保证。

### 根因 4（P1・语义缺陷）：数量字段 LWW 不可交换 → 家庭并发扣库存必错

这是**家庭场景特有、也是影响最大**的一类问题：

- 妈妈手机：牛奶 5 → 4（吃掉 1），产生 patch `{quantity: 4}`
- 爸爸手机（离线）：牛奶 5 → 3（吃掉 2），产生 patch `{quantity: 3}`
- 同步合并：LWW 后写者胜 → 结果 3 或 4，**真实库存应是 2**

字段级 LWW 对名称/位置/分类这类"赋值语义"字段是对的，但对 `quantity` 这种"增量语义"字段，绝对值补丁天生不可交换。业界标准解法：**计数器用 CRDT（PN-Counter）或同步增量（delta）而非状态**。

当前系统其实已经有增量信息（每条出库记录都带 quantity），但同步层没有用，传的是绝对值。

### 根因 5（P1・逻辑失效）：折叠场景下"尾事件确认"谓词失效 → 推送未确认死循环

**位置**：L4626-4644

回读验证只查"本地待推事件是否出现在云端 `events` 数组里"。但折叠后，本地事件可能全部进了**快照**而不在保留的 20 条事件里 → 永远确认失败 →

1. `pendingEvents` 永不清空；
2. 每次同步都 `needPush=true` → 每次都 PUT（jsonbin 免费约 1 万次请求，白白燃烧配额）；
3. 界面长期挂"推送未确认"提示——即 v2.17.1 changelog 里"始终提示推送未确认"当时只修了 413 这个诱因，**谓词本身的缺陷还在**。

### 根因 6（架构天花板）：jsonbin 单文档"读-改-写"，无 CAS

每次同步 = GET → 本地合并 → PUT 全量覆盖。两台设备同时同步时，后 PUT 者覆盖先 PUT 者（lost update）。现有缓解（回读验证 + 幂等重推）保证**最终不丢**，但：

- 没有 If-Match/ETag 之类的条件写，冲突不可避免，只能靠重试收敛；
- 每次同步固定 2 GET + 1 PUT（回读验证多一次 GET），配额消耗 ×3；
- 这是传输层限制，**引擎修得再好也无法根除**，只能降低发生率和代价。

### 次要隐患清单（P2）

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| a | fetchCloudRecord L4440 / PUT L4617 | fetch 无超时 | 网络黑洞时 `syncInFlight` 长期不释放 → 本次会话所有后续同步被 skip |
| b | makeEvent L4302 | 事件 id = deviceId + 内存 lastSeq | 同一设备开两个标签页 → seq 各自递增 → **id 撞车**，按 id 去重时静默吞掉一个事件 |
| c | 全局 | 无 `online` 事件监听、失败无退避 | 断网恢复后不会自动补同步，要等下次操作/启动；失败时固定 15s 后重试 |
| d | L4573 | barcodeCache 只增不删 | 长期可胀破 100KB 上限（即使 gzip） |
| e | importData L3956 | 导入旧备份 = 全量差分事件洪水 | 一次产生几百条事件；且旧备份里的已删商品会复活（与根因 2 叠加） |
| f | L4727 | 启动 10 分钟节流 + 无切回前台触发 | 家人刚改的数据，另一台设备最长 10 分钟才可见 |
| g | importData 注释 L3972 | 注释还是旧引擎语义（"并集+取新"） | 误导后续维护 |

## 三、改造方案（分步实施）

> 原则：**不动引擎骨架，逐一修复正确性；再补语义；最后考虑传输层升级。**
> P0 三步互相独立但都改 `cloudSync` 推送段，建议合成一个版本（v2.18.0）发布。

### 第 1 步（P0）：修复折叠 —— 快照增量演进 + knownIds 累积

**改哪里**：L4589-4611 折叠段。

**怎么改**：
```js
// 新快照 = 旧快照 + 被折叠事件的效果（增量演进，而不是从空重放）
const prev = cloudSnapshot || null;
const toFold = prev ? eventsAfter(dropped, prev.upToId) : dropped;
const dropState = replayState(prev, toFold, []);
// knownIds 跨折叠累积（墓碑永不丢）
const knownIds = [...new Set([...(prev && prev.knownIds || []), ...dropped.map(e => e.kind + ':' + e.key)])];
snapshot = { products: dropState.products, records: dropState.records,
             settings: dropState.settings, upToId: dropped[dropped.length-1].id, knownIds };
```

**预期效果**：任意多次折叠后云端数据完整；删除墓碑永久有效；老设备复活僵尸商品的通路被彻底关闭。覆盖根因 1、2。

### 第 2 步（P0）：重放改为单一流全序应用

**改哪里**：`replayState()` L4390-4391。

**怎么改**：云端事件与本地待推事件合并后按 `(ts, id)` 一次排序、一次应用：
```js
const all = [...eventsAfter(cloudEvents, snapshot && snapshot.upToId), ...(pendingEvents || [])];
all.sort(eventOrder).forEach(apply);
```
（配合第 1 步后，guard 补的 upsert 事件 ts 一定晚于云端已见事件，语义不变。）

**预期效果**：全系统真正一个事件顺序；A 设备删除/清空后，B 设备的旧离线编辑不会再把数据顶回来；delete-wins 语义成立。覆盖根因 3。

### 第 3 步（P0）：修复推送确认谓词

**改哪里**：L4626-4644。

**怎么改**：确认条件从"尾事件在 events 数组里"改为两条件之一：
1. 事件 id ∈ 云端 events；**或**
2. 该事件 ≤ 云端 `snapshot.upToId`（按 eventOrder 比较）——即已被折叠进快照。

同时校验回读到的 `syncedAt` 等于本次推送写入的值（识别"回读期间被别的设备覆盖"，此时保留队列下次重推）。

**预期效果**：确认逻辑在折叠/不折叠场景都正确；"推送未确认"只在真实失败时出现；pendingEvents 正常清空，不再空转 PUT 烧配额。覆盖根因 5。

### 第 4 步（P1）：数量改为增量（delta）事件 —— 家庭并发核心修复

**改哪里**：`diffToEvents()` + `replayState()` + 库存操作入口（incrementStock / decrementStock / submitProduct / executeRevoke / saveEdit）。

**怎么改**（混合语义，改动最小）：
- 库存加减/吃完/浪费/撤销这类**增量操作**：生成 `{op:'delta', key: productId, patch:{quantity: -1}}`；
- 编辑弹窗手动改数量、录入新商品：仍是 `upsert`（赋值语义）；
- `replayState` 的 apply 增加 delta 分支：`st.quantity = (st.quantity||0) + delta`；
- 排序后 delta 与 upsert 按全序混合应用，天然收敛（所有设备算同一笔账）。

为拿到"操作意图"而不是事后差分，需要在库存操作函数里直接产生 delta 事件（`makeEvent('product','delta',...)` 后 `persistSyncState()`），diffToEvents 对 quantity 字段跳过（避免重复计数）。

**预期效果**：妈妈吃 1 件 + 爸爸吃 2 件 = 云端减 3 件，与设备上线顺序无关；家庭最频繁的冲突类型从"必错"变"必对"。覆盖根因 4。

### 第 5 步（P1）：健壮性补齐（超时 / 多标签 / 断网恢复）

| 改动 | 位置 | 做法 | 效果 |
|---|---|---|---|
| fetch 超时 | L4443 / L4617 | AbortController，GET/PUT 各 15s | syncInFlight 不再卡死，本次会话同步可自愈（隐患 a） |
| 事件 id 加标签页随机后缀 | makeEvent L4302 | id = `dev-xxx:tab-yyyy:seq` | 双标签页 id 不撞车（隐患 b） |
| online 监听 + 指数退避 | onMounted | `window.addEventListener('online', …)` 立即补同步；失败后 30s→60s→5min 退避 | 断网恢复即刻收敛，弱网不空转（隐患 c） |
| 切回前台触发同步 | visibilitychange | 距上次同步 >2 分钟则拉取 | 家人改动更快可见（隐患 f） |

### 第 6 步（P2）：卫生项

- barcodeCache 修剪：只保留最近 90 天 `updatedAt` 的条目（或上限 500 条 LRU）→ 防胀破 Bin（隐患 d）；
- importData：导入前弹确认"导入将覆盖合并到云端"；导入后重置 `syncState.baseState` 并立即 `diffToEvents()`；更新过时注释（隐患 e、g）；
- 测试补齐：在 `_test_sync_v217.js` 增加 3 个用例——**二次折叠数据完整性**、**折叠后老设备不复活僵尸**、**并发 delta 数量收敛**。

### 第 7 步（可选・架构层）：传输层评估

引擎修好后，jsonbin 的"无 CAS 全量覆盖"仍是天花板。如果后续还想更稳，三条路：

| 方案 | 成本 | 收益 | 建议 |
|---|---|---|---|
| A. 留在 jsonbin + 上述修复 | 0 新设施 | 冲突率随修复大幅降低；家庭 2-5 台设备错峰使用，实际冲突极少 | **现阶段推荐** |
| B. Cloudflare Worker + KV/D1（免费额度） | 1-2 天 | 支持按事件追加 + 条件写，冲突从根上消失；请求成本归零 | 中期可选，API 层可平滑替换 fetchCloudRecord/PUT 两处 |
| C. Supabase/Firebase 实时库 | 迁移工作量大 | 实时推送、成熟冲突处理 | 对家庭小项目过重，不建议 |

**先做 1-6 步，观察一个版本周期；若仍出现并发覆盖再评估 B。**

## 四、修改项 → 预期效果 总表

| 步骤 | 覆盖根因 | 解决的现存问题 | 预期效果 |
|---|---|---|---|
| 1 折叠修复 | 根因 1、2 | 商品/记录莫名消失、僵尸复活 | 任意次折叠数据完整，墓碑永久有效 |
| 2 全序重放 | 根因 3 | 清空/删除被旧设备编辑顶回 | 删除语义可靠，全系统收敛一致 |
| 3 确认谓词 | 根因 5 | "推送未确认"反复出现、配额空转 | 状态提示真实，请求量降约 1/3+ |
| 4 数量 delta | 根因 4 | 多人同时扣库存数量错乱 | 库存数量并发收敛，账本与库存一致 |
| 5 健壮性 | 隐患 a/b/c/f | 同步卡死、双标签丢事件、断网不补同步 | 弱网/多标签/断网场景自愈 |
| 6 卫生项 | 隐患 d/e/g | 缓存膨胀、导入复活僵尸 | 长期运行不触顶 |
| 7 传输层 | 根因 6 | 并发覆盖（理论残留） | 视观察结果决定 |

## 五、验证方式（每步落地后）

1. 单元级：把 `replayState / 折叠 / 确认谓词` 抽成可注入纯函数（或继续用 `_test_sync_v217.js` 的 Playwright + 模拟 jsonbin 路线），跑第二节列出的新增用例；
2. 双设备端到端：两个浏览器上下文 + 共享内存 bin，覆盖"离线编辑→对方删除→上线""双方同时吃库存""老设备周后上线"三个家庭剧本；
3. 灰度：发布前本地 `window.__foodin.cloudSync()` 手动触发回归一遍，确认云同步状态提示文案与真实结果一致。
