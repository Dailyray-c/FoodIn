## 2. 运行时架构：没有构建框架的单文件应用

```
浏览器
 └─ index.html（801,622 字节 ≈ 783 KB / 11,388 行，唯一应用文件）
     ├─ 1–29      head：本地 Vue（vendor/vue.global.prod.js，onerror 才多源回退）
     ├─ 30–625    <style>①：UI 规范层（:root 令牌 + 54 个 .fi-* 组件类）
     ├─ 632       <link styles.css>  Tailwind 预编译产物（必须排在组件类之后）
     ├─ 633–746   <style>②：fontScale 三档等值规则
     ├─ 748–4290  <div id="app"> 内联 in-DOM 模板（8 个页面 + 全局浮层）
     └─ 4291–11375 <script>：createApp(4319) → setup() → return{}(11305) → mount
         └─ 11376–11385  Service Worker 注册
```

- **唯一的「构建」动作** = 重编译 Tailwind（`src/tailwind.css` + `tailwind.config.js` → `styles.css`，产物入库）
- **发布** = 静态文件推 GitHub Pages（`deploy.yml` 白名单 `cp` 到 `_site/`）
- Vue 3.5.42 **本地化**，用的是**含运行时编译器的完整版**（因为模板是 in-DOM 模板）
- `package.json` 只有 `tailwindcss` + `playwright` 两个 devDependency；无 SFC、无模板文件、无打包步骤
- `tailwind.config.js` 的 `safelist` 兜住「拼接生成/易漏」的类：负值定位、`-translate-y-1/2`、`grid-cols-5..8`、`peer-checked:bg-*-500`

**这条约束决定了本项目绝大多数历史 Bug 的形态**：没有模块系统、没有类型检查、没有组件文件。所有状态与函数共处一个 `setup()` 作用域，靠**两份手写白名单**对外暴露（§14）。

## 4. 数据模型（以线上真实数据为准）

从 `backups/latest.json`（2026-09-20 真实云端快照，151 商品 / 446 流水）反推，与代码构造点交叉验证。

### 4.1 product

**权威构造点 5 处**：`submitProduct`(7498-7518)、`submitBatchItem`(7551-7571)、`seedDemoData`(7090-7111)、`executeRevoke` 快照重建(6810-6815) 与降级重建(6827-6842)。

| 字段 | 类型 | 含义 | 空值 |
|---|---|---|---|
| `id` | string | 主键。`crypto.randomUUID()`，降级 `Date.now().toString(36)+rand`(6057-6060) | — |
| `name` | string | 商品名（提交前过 `cleanWithNotice` 名称清洗） | 必填 |
| `barcode` | string | 条码 | `''` |
| `location` | string | ❗**逗号字符串**（`, ` 分隔）；表单态是数组 | `''` |
| `category` | string | 同上 | `''` |
| `stockInDate` | string | 入库日 `YYYY-MM-DD`（本地时区 `getTodayStr` 4881） | 今天 |
| `productionDate` | string | 生产日期 | `''` |
| `expiryDate` | string | 到期日 | `''` |
| `shelfLife` | string | **文本**如 `"12个月"`；历史纯数字按「天」解析 | `''` |
| `quantity` | number | **当前剩余件数**（核心字段） | 1 |
| `brand` / `spec` / `netContent` / `manufacturer` | string | 品牌 / 规格 / 净含量 / 厂家 | `''` |
| `price` | number \| `''` | ❗**多件总价，不是单价**；`''` = 未填（**≠ 0**） | `''` |
| `imageUrl` / `note` | string | 图片链接 / 备注 | `''` |
| `createdAt` / `updatedAt` | string | ISO 时间戳（导入/去重按 `updatedAt` 比新旧 9219-9223） | now |
| `reheatCount` | number | **可选、懒创建**；仅剩菜加热 +1，读时 `|| 0` | 可能不存在 |
| `__demo__` | bool | `DEMO_MARK`(7050) 导览示例标记，同步引擎完全剔除 | 仅示例 |

**「单件商品」vs「多数量」**：一个 SKU = **一个对象**，数量存在 `quantity: N`，**绝不往数组塞多条**；不存在 `qty`/`count` 字段。归零即移出并删对象（`eatOne` 6918-6921 / `purgeGhostProducts` 11177-11178）→ **库里不存在 `quantity: 0` 的滞留对象**。

**归一化**：`saveData` 必先跑 `normalizeProductList`(4383) → `normalizeProductInPlace`(4376) → `normalizeTagText/List`(4357-4372)，把 `location`/`category` 统一为「去空白 + 去空 + 字段内去重 + `, ` 拼接」。
⚠️ 模型约定：**落库为字符串、表单为数组**。v2.36.0 前无快照重建曾写 `location: []`（数组），已在 6831-6834 修掉 —— **新代码别把数组写进商品**。

### 4.2 record（流水）

**唯一构造入口 `addRecord(data)`(6513-6542)**，返回新记录供 `saveUndoSnapshot` 关联。

| 字段 | 说明 |
|---|---|
| `id` | 主键（也是撤销快照的 key） |
| `type` | `in \| eat \| waste \| adjust \| reheat` |
| `productId` | 关联商品 id，可为 `''`（示例数据） |
| `productName` / `barcode` | **快照**（商品删了流水仍可读） |
| `quantity` | 带符号件数，符号约定见下 |
| `detail` | 明细。❗**格式是契约**：`字段label：before → after`，多段用 `·` 分隔（`undoChangedFromDetail` 6638-6650 依赖它） |
| `unitPrice` | ❗**单件单价快照** = `price/quantity`，2 位小数(6532) |
| `netContent` | 净含量快照 |
| `reason` | 浪费原因**枚举 value**（非中文）：stale/spoiled/tired/overbought/other(4329-4335) |
| `createdAt` | ❗**唯一时间戳**（没有 `date`/`ts`/`updatedAt`）；筛选、按天分组、趋势全基于它 |
| `__demo__` | 示例标记 |

**五种 `type`**（`recordTypeOptions` 4723-4730 是 UI 真源）：

| type | 标签 | `quantity` | `detail` 示例 | 触发 |
|---|---|---|---|---|
| `in` | 入库 | **正** `+N` | `新增入库 +3` / `批量入库 +2` | `submitProduct`/`submitBatchItem`/`incrementStock` |
| `eat` | 吃完 | **负** `-1` | `正常吃完 -1` / `吃完一份 -1`（剩菜） | `eatOne` |
| `waste` | 浪费 | **负** `-p.quantity` | `删除商品，浪费 3 件（放过期了）` | `executeWasteDeleteWithReason` |
| `adjust` | 调整 | **0** | `分类：调味品 → 零食饮料 · 价格：5 → 8` | `saveEdit`/`applyCleanHistory` |
| `reheat` | 🔥 加热 | **0** | `加热一次（第 2 次）` | `incrementStock` 剩菜分支 |

### 4.4 `places`：两级「地点 → 分区」

```json
{ "name":"冰箱", "zones":["冷藏","冷冻海鲜抽屉"],
  "partitioned":true, "layout":"", "newZoneInput":"" }
```

- `zones` 是**字符串数组**（不是 `[{name}]`）
- `layout` / `newZoneInput` 是**表单临时态**；上云前由 `placeSyncCopy()`(4433-4437) 剔除 `newZoneInput`
- 现行数据：厨房 / 冰箱(6 分区) / 餐厅阳台 / 餐桌 / 餐边柜
- **按地点批量操作的唯一正确判据**：`loc === pl.name || pl.zones.includes(loc)`
- ❗**删地点 ≠ 改地点**：删 → 命中商品 `location` **一律清空**；改 → **只改「存地点名」那批**，分区商品不动（靠 `placeOfTag` 跟随新名）
- `settings.locations` **已废弃**，唯一真源是 `places`；`migrateLooseLocationsToPlaces()`(9947-9963) 仅兼容旧数据，3 处调用：`loadData`(6492)、导入(9249)、云同步(10773)

### 5.1 `saveData()` 骨架与节流

```js
products.value = normalizeProductList(products.value);   // 6439 必须在 diffToEvents 之前
normalizeSettingsCollections();                          // 6440
settings.localModified = new Date().toISOString();       // 6441
try { /* 写 4 个 key */ } catch { toastErr('本地保存','浏览器存储空间不足或被禁用'); }  // 6443-6447
if (云同步已配置) { try { diffToEvents(); } catch {}     // 6450 事件先落盘
  clearTimeout(cloudPushTimer); cloudPushTimer = setTimeout(() => cloudSync(false), 15000); }  // 6451-6453
```

- ❗**`saveData()` 自身无节流**，每次全量 `JSON.stringify` 三个大对象；唯一的写侧防抖是**云推送 15 秒**
- ❗**批量录入会重复全量写盘**：`submitBatchItem` 每条都调 `saveData()`（7577）→ N 条 = N 次全量写

### 5.2 异常兜底与迁移

⚠️ **`loadData()` 是最高优先级技术债**：4 个 `JSON.parse` 共用**一个** `try/catch`(6500)。若 `products` 的 JSON 损坏 → 直接跳 catch → `records`/`settings`/`barcodeCache` **全部不加载**（保持空），随后任何一次 `saveData()` 就把空值写回盘 → **一次坏数据 = 永久丢失**。

**没有版本号迁移框架**：不存在 `migrate()`/`migrations[]`，全是「字段缺失即补默认」的幂等内联补丁（`loadData` 6468-6497：`ocrGroupMode`/`ocrImageEnhance`/`nameClean*` 补齐、`places` 类型、`builtinCategories` 兜底、`fontScale` 枚举校验、`leftoverDefaultDays` 夹取 1-30、`zones`/`partitioned` 类型补齐）。

## 6. 云同步：事件溯源引擎（本项目最复杂的子系统）

核心代码块 **10406–11131**；动手前先读 **10406–10432 的设计说明块**（自述 6 条设计约定 + 3 个 v2.18.0 根因修复）。

### 6.1 后端与契约（Upstash Redis REST）

| 动作 | 请求 |
|---|---|
| 读 | `GET {url}/get/foodin%3Async`，header 仅 `Authorization: Bearer <token>`，15s 超时 |
| 写 | `POST {url}/set/foodin%3Async`，`Authorization: Bearer <token>` + `Content-Type: text/plain`，**值走 body** |

- `CLOUD_DOC_KEY = 'foodin:sync'`(10709)，**必须与 `scripts/cloud_io.py` 的 `DOC_KEY` 一致**
- `cloudEndpoint()`(10710) = `cloudBinId` 去尾斜杠；**字段名沿用历史**（`cloudBinId`=URL、`cloudApiKey`=Token），二者都是本机专属，不进 schema
- ❗**绝不能把负载拼进 URL**（gzip+base64 后仍数十 KB，实测 92.8KB）
- 无 TTL/EX、无 pipeline/transaction、**无条件写（无 CAS）**
- **架构真相**：物理上是「**拉整份 → 内存合并 → 整份覆盖写**」的单文档模式，并没有用 `RPUSH` 等真实 append —— 所谓「事件只增不改」是**逻辑语义**而非存储语义
- 错误翻译：`cloudErrText`(10713-10721)：401/403「令牌无效或权限不足」、413「数据超出云端容量上限」、429「请求过于频繁，已被限流」、≥500「云端服务暂时不可用」；`cloudBadgeFromReason`(10724-10732) 出短徽标

### 6.2 云端文档：v2 内层 + v3 压缩信封

内层（11035，与线上快照实测一致）：

```json
{ "schemaVersion": 2,
  "syncedAt": "…",
  "events":  [ /* ≤30 条 */ ],
  "snapshot": { "products": [...], "records": [...], "settings": {...},
                "upToId": "dev-xxx:v4w8:511", "knownIds": ["record:…", …] },
  "barcodeCache": {...} }
```

外层（10652-10674）：`{schemaVersion:3, compressed:true, algo:'gzip', data:<base64>}`，用 `CompressionStream`；不支持则回退 v2 明文（11038-11039）。`scripts/daily_backup.py` 的 `decode_record()` 负责解这层。

### 6.3 事件结构

```json
{ "id":"dev-mu18nas236543m:5j51:489", "ts":"2026-09-20T12:01:39.952Z",
  "kind":"product", "op":"delta", "key":"pmu9mfzcc528sdp",
  "patch": { "delta": -1, "quantity": 1 } }
```

- `id` = `deviceId + ':' + tabNonce + ':' + lastSeq`(10486) —— **设备 + 标签页 + 单调序号**。❗**格式是跨设备去重的唯一基础，不可改**
- `deviceId` = `'dev-' + Date.now().toString(36) + rand(6)`(10474)，持久化在 `food_inventory_sync_v2`
- `ts` 是 **Lamport 式水位**：`new Date(Math.max(Date.now(), lastSeenTs + 1))`(10483)
- `eventOrder`(10563)：先 `ts` 升序，`ts` 相同按 `id` 字典序 → **全系统单一全序**
- `kind` ∈ `product | record | setting`；`op` ∈ `upsert | delta | delete`
  - `delete` 只用于 product/record，`patch = null`；`delta` 只用于 product，`patch = {delta, quantity}`；**`setting` 只有 upsert，`patch` 就是值本身**(10627)
- **幂等性**：upsert/delete 天然幂等；**delta 必须恰好一次** —— 这是所有 id 去重的核心动机（10582-10584 注释：delta 被应用两次会导致数量双计）
- **冲突语义**：product/record 字段级 LWW（`fieldPatch` 10489）；`quantity` 走 PN-Counter 式 delta 累加（下限 0，10599-10603）；setting 整值覆盖

### 6.4 两条 append 通道

1. **`diffToEvents()`(10498-10531)**：`captureState()` vs `syncState.baseState` 差分 → 逐字段 `fieldPatch` → 缺失 id 发 delete；settings 由 schema 遍历差分。调用点 `saveData`(6450)、`cloudSync` 拉取后(10881)
2. **`emitStockDelta()`(10538-10549)**：数量增减的独立通道。统一入口 **`applyStockDelta(product, delta)`(10551-10561)** 改数量后发 delta，并 ❗**同步把 `baseState` 里该商品 `quantity` 改成结果值**(10545-10548)，否则下轮 diff 会再发一条绝对值 upsert 造成**双计**

**示例数据双处拦截**：`captureState`(10439-10440) 过滤 + `applyStockDelta` 对 demo 商品直接 return(10559)。

### 6.5 折叠（compaction）

`allEvents.length > 30` → 保留**最后 20 条**(11003-11004)，其余折叠进 `snapshot`，用最后一条事件的 `id` 作新 `upToId`，实体 id 累积进 `knownIds`(11015-11033)。

- **远端 `events` 长期只有 ≤30 条**（线上实测 23 条即印证）
- **本地只有「待推队列」`pendingEvents`**（上限 5000，超限丢最旧，10526/10541）；**没有**「已应用事件日志」的本地副本
- `baseState` **不落盘**，启动由 `captureState()` 重建
- ❗v2.18.0 核心修复：**在旧快照之上增量重放**(11014) + **`knownIds` 跨折叠累积**(11019-11021) —— 否则旧墓碑随折叠丢失，几周没开机的老设备会让已删商品复活

### 6.6 主流程与铁律

`syncState = { deviceId, lastSeq, lastSeenTs, pendingEvents, baseState, lastSentSyncedAt, lastSentIds }`(10424)

`cloudSync()`(10835)：**有变更固定 3 次请求**（GET 拉取 10845 → POST 推送 11041 → GET 回读校验 11058）；稳态无变更 1 次。

❗**铁律：先拉取，拉不到绝不下发** —— 拉取失败即 `return {ok:false}`，走不到推送分支。服务端故障时云端**不会被覆盖**，待推事件留在 `food_inventory_sync_v2`，恢复后自动补推（故障期实测 0 次 PUT）。

- **并发保护**：`syncInFlight`(10834/10837) 重入返回 `{ok:false, skipped:true}`
- **推送确认三重谓词**(11051-11069)：① 回读 `syncedAt` 全等 → 清空队列；② 否则按事件 id 是否出现在回读 `events` 里做部分确认；③ 仍有剩余则保留待重推。**跨轮兜底**(10858-10865)：`lastSentSyncedAt === rec.syncedAt` 时用 `lastSentIds`（最近 2000）精确移除
- **失败退避**：30s 起、每次 ×2、**封顶 5 分钟**(10821-10828)；成功即复位。定时器是内存态，刷新即丢（靠启动补推）
- **反误删守卫**(10887-10929)：`cloudKnown = knownIds ∪ 快照现存实体 ∪ 增量事件 key`；本地有 + 重放结果缺失 + 云端从未认识 → 补 upsert（判为本地新增，不是删除）
- **重放 `replayState`**(10585-10647)：快照初始化 → 逐事件 apply（**v2.34.0：孤儿且 patch 无 name 的事件直接丢弃**(10617-10621)，防 `{quantity:3}` 空卡片）→ 合并 cloudAfter+pending 并**按 id 去重** → 排序一次 apply → 归一化 places/categories(v2.36.1) → 返回

### 6.7 `SETTINGS_SYNC_SCHEMA`（4449-4469）—— 设置同步的唯一注册表

**13 项**，字段属性 `{key, type, default, mode?, values?, allowEmpty?}`，`mode` ∈ `replace`(默认) / `union` / `localFirst`。

**驱动 6 处**（新增字段只改一处）：`captureState`(10442)、`diffToEvents`(10520)、`replayState` 初始化(10591)、重放应用(10936-10951)、guarded 补推(10913-10924)、`applyLegacyUnion`(10776)。

- `number` 用 `!!v` 排除 0；`string` 非 `allowEmpty` 排除空串；`values` 白名单（`settingApplyOk` 4480-4487）
- `localFirst`：本机值合法就保留，**且本地合法但云端不一致时主动回推云端**(10920-10924)
- ❗**v2.36.1 关键语义**：**空数组是合法值**(4478-4479)，支持「清空全部储存地点」传播；字段**存在性**由 `replayState` 的 `null` 判定负责
- ❗**空串合法必须 `allowEmpty: true`**，否则 `settingApplyOk` 判空失败 → 「清空后再也同步不出去/拉不回来」

**独立于 schema 的同步通道**：`barcodeCache` 走 payload 顶层字段，按 `updatedAt` 取新并集 + 修剪 **180 天 / 最多 500 条**(10972-10985)。
**明确不上云**：撤销快照 `undoCache`。

## 7. 撤销机制（v2.31.0 真撤销 / v2.32.0 收窄到「本条」）

**存储**：`food_inventory_undo_cache`（纯本机，刻意不进云）

```js
undoCache.value[recordId] = {
  product: <变更前完整商品深拷贝>,        // cloneProduct 6566 JSON round-trip
  at: ISO,
  changed: ['category','price'] | null    // v2.32.0 本条实际改动过的字段名
}
```

上限 **300 条**(6552) / TTL **60 天**(6553)；`pruneUndoCache`(6571-6584) 三重修剪（孤儿 / 超 TTL / 超量）。

**写入点 5 处**（都是「先 cloneProduct 再改」）：加热 6889、吃完 6913、浪费删除 7189、编辑调整 7373、名称清洗 9602。
❗**入库路径不写快照**（7520/7573/6898）→ 撤销入库只能走降级分支（6767-6796）。

### 「只还原自己操作过的字段」——三层降级

1. **本机快照 = 天然的边界**：`getUndoSnapshot`(6599-6602) 只查本机 map；别的设备/别人建的流水 → `null` → 走旧逻辑，**别人的数据保持原状**
2. **字段级回退**（v2.32.0，`changed` 数组）：`executeRevoke` 6846-6851 只回填本条改过的字段。动机(6716-6718)：旧版无条件整快照覆盖会把「别的流水造成的数量变化」一起吞掉（只改过分类的记录，撤销时不该动数量）
3. **从 `detail` 反推**（兼容老缓存）：`undoChangedFromDetail`(6638-6650) 按 `·` 切段 → 取 `：` 前 label → 经 `UNDO_KEY_BY_LABEL`(6621，由 17 字段的 `UNDO_FIELD_LABEL` 6614-6619 反转)映射回字段名

**数量的特殊规则（关键）**：❗**数量一律走「delta 反向」而非快照绝对值**（注释 6669-6670）。同一商品可能有多条同类流水（吃两件 = 两条 eat），用快照绝对值撤销第一条会把第二条的效果一起吞掉。
- **eat/waste 且商品仍在库** → `undoFillEmpty`(6654-6664) 只「补空」不覆盖，跳过 `['quantity','reheatCount']`
- **eat/waste 且商品已被移出** → 完整重建 `{...snap, id, quantity: max(1,...), updatedAt}`(6810-6815)
- **`reheat`** → `reheatCount - 1` **增量**回退

`revokePreview`(6671-6736) 生成预览，`kind` ∈ `note/reheat/delete/qty/restore/adjust/qtyonly`；`executeRevoke` 末尾删流水 + `dropUndoSnapshot` + `saveData`(6857-6860)。

存储是**文本**（`"12个月"` / `"2年"` / `"90天"`），但❗**线上仍有 22 个纯数字日数**（旧数据，129 个字符串 / 22 个数字）。

### 11.2 OCR 三引擎（不是单一 Tesseract）
分派在 **`runOcr(canvas)`(8583-8649)**，`settings.ocrEngine` 默认 `'paddle'`：

- `paddle`(8627-8635) → 失败/空 → `tryTesseractOcr`，用 `ocr.paddleNote` 说明「为什么选了 Paddle 出来的是 Tesseract」

## 15. 构建、CI 与发布链路

### 15.1 构建
```bash
./node_modules/.bin/tailwindcss -i ./src/tailwind.css -o ./styles.css --minify   # = npm run build:css
```
**只有新增「从未出现过」的 utility class 才需重编译**；改 `.fi-*` 组件类 / JS / 模板条件不需要。
未编译的症状极具欺骗性：**功能全对，只是样式失效或高度塌陷为 0（用户点不到按钮）**。
> 校验类是否已进 CSS 必须 `grep -o 'lg\:mt-auto'`；`grep -c` 因 minified 只有一行**永远返回 1**。

### 15.2 CI（3 条 workflow）
| Workflow | 触发 | 作用 |
|---|---|---|
| `deploy.yml` | push master/main | 白名单 `cp` 到 `_site/` → upload-pages-artifact → deploy-pages |
| `daily-backup.yml` | cron-job.org `workflow_dispatch`（+ 备用 schedule） | 读云 → `backups/inventory-YYYY-MM-DD.json` + `latest.json`，保留 30 份，自动 commit `[skip ci]` |
| `daily-expiry-check.yml` | cron-job.org | 读云 → 临期/过期检查 → 企微群机器人，Server酱可选 |

共享 `scripts/cloud_io.py`：`resolve_backend()` 优先 Upstash、回退 jsonbin；`fetch_cloud()` 硬失败抛异常，`put_cloud()` **只告警不抛**。
> ❗**同一契约三处**：改 `DOC_KEY`、负载结构或压缩方式 **必须同步改 `cloud_io.py`**，否则定时任务直接挂。
> ❗**三方一致性**：`deploy.yml` 拷贝清单 ⊇ `PRECACHE_ASSETS` ⊇ 页面 `src="./…"`；新增顶层目录必须加 `cp -r <dir> _site/`。

### 15.3 Service Worker
白名单模式：**只拦同域静态 + `CDN_RESOURCES`**，其余（所有第三方 API）一律不 `respondWith`，永不缓存（v2.24.4 根治 API 缓存污染）。
- 导航请求网络优先；静态资源 cache-first + 后台 revalidate；**失败返回 504**，不伪造首页 HTML
- 预缓存 `Promise.allSettled` 逐资源（替代 `addAll` 全有全无）+ 失败点名日志
- ❗改动 `index.html` / `styles.css` / `service-worker.js` / `vendor/` 任一项 → **必须 bump `CACHE_NAME`**

### 15.4 发布与回退
```bash
mkdir -p versions/vX.Y.Z && cp index.html service-worker.js styles.css versions/vX.Y.Z/   # 备份三件套
./push-safe.sh "release(vX.Y.Z): 说明"
```
- `push-safe.sh`：白名单提交 + `versions/` 全量；**绝不 `git add .`/`-A`**；**绝不用 `git stash`+`rebase`**（曾写坏 `.git`）；流程 `fetch → reset --mixed FETCH_HEAD → add 明确文件 → commit → push`
- `push-clean.sh`：`git add -u` + `docs/`（**新增 docs 必须走这个或手动 add**）
- 回退 `cp versions/vX.Y.Z/* .` —— ❗但有 3 个目录名不实（§17.1）

## 16. 后续开发：必守清单

### 16.1 改代码前
1. 改 UI → **先读 `UI规范.md`**；改数据结构 → 先看 §4/§5/§6 的兼容性约束；写测试 → 读 `docs/E2E测试手册.md`

### 16.2 改代码时（五条铁律）
1. ❗**同文件多 Edit 必须串行**（同一消息并发多个 Edit 只有 1 个生效，其余静默丢失）
2. ❗新增函数/状态**同时进 `return{}` 与 `window.__foodin`

### 17.1 版本档案（`versions/`）存在「张冠李戴」

逐一校验 34 个目录名与内部实际版本：**31 个自洽，3 个装的是「上一个版本」**：

**建议**：统一为 **bump 完成后**备份（目录名 = 内部版本号），或明确改名为「上一版快照」；并修正这 3 个目录。

### 17.5 代码级风险（按优先级）

| # | 风险 | 位置 | 说明 |
|---|---|---|---|
| 1 | ❗**`loadData` 单一 try/catch** | 6500 | 4 个 `JSON.parse` 共用一个 catch：`products` 损坏 → `records`/`settings`/`barcodeCache` 全不加载（保持空）→ 随后任一 `saveData()` 把空值写回盘 = **一次坏数据永久丢失** |
| 2 | **`importData` 会覆盖云同步凭据** | 9236-9237 | 无条件 `settings.cloudApiKey/cloudBinId = obj.*` → 导入别人的备份会把本机云配置改掉（对「换机迁移」是特性，对「只想恢复库存」是陷阱） |
| 3 | **`importData` 未重置 `syncState.baseState`** | 9266 | 导入后直接 `saveData()` → 对旧基线差分 → 把整份备份作为「新增事件洪水」推上云。改造方案文档第 6 步即此，**未落地** |
| 4 | **`settings.cloudLastSync` 语义混用** | 11088 | 该行在**推送失败**路径也会执行（分支不 return）→ 设置页「上次同步」不是「上次成功时间」；而它同时被启动 10 分钟节流(11275)与回前台 2 分钟判定(11289)使用 → 推送连续失败时会**长期不再尝试拉取** |
| 5 | **折叠 + delta 的重放双计风险**（推断，未实测） | 10585/11003/11051 | 若本轮发生折叠（delta 已进快照、从 `outEvents` 移除）而推送确认失败，且下轮拉到的 `syncedAt` 与 `lastSentSyncedAt` 不等，则跨轮兜底(10858)与 id 可见性检查(11063)双双失效 → delta 留在 `pendingEvents`，而 `replayState` 又会在**已含它的快照**之上再应用一次 → **数量多扣**。upsert/delete 幂等无此问题 |
| 6 | **`dedupeProductIds` 只写 localStorage、不进事件流** | 7032-7037 | 重新分配的 id 不同步、旧 id 无墓碑 → 多设备各自自愈可能长期分叉 |
| 7 | **客户端无任何体积/额度预检，无分片** | 全仓 | 100MB 单值上限只存在于注释/changelog；413/429 只翻译成文案，**没有降级/分片/暂停策略**。诊断文档实测：1000 商品+5000 流水 = 93.9KB |
| 8 | **长期膨胀点** | 11015-11021 / 11022 | `snapshot.knownIds` **只增不减**（无上限、无压缩）；非折叠分支会把全量事件留在远端 `events` |
| 9 | **`saveData()` 无节流 + 批量重复全量写盘** | 6436 / 7577 | `submitBatchItem` 每条都调 → N 条 = N 次全量 `JSON.stringify` 三个大对象，大库存下是主线程阻塞点 |
| 10 | **无版本号迁移框架** | 6468-6497 | `settings.version` 永远等于 `CURRENT_VERSION`（4341/11229）**不能当迁移判据**；现有迁移全是幂等「字段缺失即补」 |
| 11 | **删字段不会生成同步补丁** | 10491 | `fieldPatch` 只遍历 live 的 key → 云端旧值残留并在下次 replay 复活 |
| 12 | 其它小项 | — | `places[]` 混入表单临时态 `layout`；商品 `shelfLife` 混合类型（129 字符串 / 22 数字）；流水三代字段形态；示例流水符号约定错误(7132/7137) |

### 17.6 同步子系统改造优先级建议（综合三份诊断文档）
① 折叠 delta 的重放风险（正确性，§17.5-5）
② 条件化回读验证（**省 1/3 请求**，诊断文档已论证）
③ `knownIds` 限容/压缩
④ `importData` 后重置 `baseState`
⑤ 修文档与 changelog 的 jsonbin / 「一键拆分」描述
> 原则（改造方案文档结论）：**引擎骨架是对的，问题集中在实现级 bug —— 不要动骨架**。
