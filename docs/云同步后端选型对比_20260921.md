# 云同步后端选型对比 · 2026-09-21

**背景**：jsonbin 免费版为「**一次性** 10,000 请求」（不按月刷新）+ 单 Bin 100KB，且 2026-09-21 发生源站宕机（HTTP 522）。
用户要求：换一个**额度按月（或按日）刷新**、且符合本项目要求的后端。

---

## 一、本项目的硬性要求（从代码读出，非推测）

| # | 要求 | 依据 | 若缺失的后果 |
|---|---|---|---|
| 1 | **浏览器可直连（支持 CORS）** | 单文件 PWA，无自建后端，`fetch` 直接从前端发出 | 只能加一层代理，改动量翻倍 |
| 2 | 读写粒度 = **单个 JSON 文档** | 引擎是「拉整份 → 合并 → 推整份」（`fetchCloudRecord` / PUT） | 需重写同步引擎 |
| 3 | **单值容量 ≫ 100KB** | 实测 1000 商品+5000 流水 → gzip 后 **93.9KB**，已顶到 jsonbin 上限 | 触发 413，同步直接失败 |
| 4 | 额度**按月/按日刷新** | 本次要解决的核心痛点 | 用完即永久失败 |
| 5 | **写后读一致**（或可容忍延迟） | 推送后立刻 `GET` 回读校验（L10686） | 验证误判 → 重复推送、事件双计 |
| 6 | 国内访问可用 | 用户在国内；jsonbin 走 Cloudflare，联通晚高峰可到 800ms+ | 同步慢、易超时 |
| 7 | 密钥可放在前端 | 现状即如此（`cloudApiKey` 存本机 settings） | 若必须保密则需引入后端 |

> 要求 5 很容易被忽略，但**它是最容易踩的坑**：很多「边缘 KV」是最终一致的。

### 关键数字（均为 2026-09-21 从官方页面核实）

**Upstash Redis 免费版**
- 数据 256MB ｜ **命令 50 万/月**（按月重置）｜ 带宽 10GB/月
- 单请求最大 10MB ｜ **单记录最大 100MB** ｜ 10,000 命令/秒 ｜ 免费 1 个数据库
- 单个主节点 → **强一致**（正好匹配「写后回读校验」）

**EdgeOne Pages / Makers 免费版**
- 边缘函数 **300 万次/月** ｜ 云函数 100 万次/月 ｜ **KV 1GB** ｜ Blob 1GB ｜ 构建 500 次/月
- 安全加速流量与请求**不限量**；官方称免费版**永久提供**
- ⚠️ **KV 目前仅支持由 Edge Functions 调用**（不能从浏览器直连）
- ⚠️ 国内节点需**已备案域名**；未备案只能选「全球可用区（不含中国大陆）」

**Cloudflare Workers KV 免费版**
- 读 10 万/天 ｜ **写 1,000/天** ｜ 删除 1,000/天 ｜ 列表 1,000/天 ｜ 存储 1GB
- **每日 00:00 UTC 重置**；单值最大 25MiB；**同一 key 每秒最多写 1 次**
- ⚠️ **最终一致**：写入后全局生效可能延迟，与「推完立刻回读校验」天然冲突

**Supabase 免费版**
- 500MB 数据库 ｜ 5GB 出流量/月 ｜ **API 请求不限量** ｜ 50k MAU ｜ 最多 2 个活跃项目
- ⚠️ **免费项目闲置 1 周后会被暂停**（需去后台手动恢复）

## 三、推荐

### 首选：Upstash Redis（REST）—— 改动最小、无服务端代码
**理由**：四条硬要求全中，且**不用写任何后端**。
- 额度按月重置（50 万命令 ≈ 16 万次同步/月），对当前用量（约 75 批次/天 ≈ 6,750 命令/月）有 **70 倍以上余量**
- 单记录 100MB，**彻底摆脱容量焦虑**（也可省掉 gzip 层，见下）
- **强一致** → 现有的「推送后回读校验」逻辑可原样保留
- 免费、免信用卡

**待你确认的一点**：它的 REST API 从浏览器直连（CORS）我本次**没能核实**（查证被拦），
需要在真实环境实测一次。若不支持，加一个极小的代理即可（此时请转向下面第二个方案）。

### 国内首选：EdgeOne Pages KV —— 延迟最好，且复用你现有部署工具链
**理由**：你本来就在用 EdgeOne 系部署；国内节点延迟可比 Cloudflare 低一个数量级；额度按月刷新且很宽（KV 1GB + 300 万次边缘函数）。
**代价**：KV 只能由边缘函数读写 → 必须写一个约 30~50 行的边缘函数当「薄封装」，
再加一个共享密钥做鉴权。**还需实测它的一致性模型**（若为最终一致，回读校验要放宽）。

### 备选：Cloudflare Workers + D1
若你希望强一致 + 大额度且不介意部署 Worker：D1（SQLite）是强一致的，适合这种「单行 JSON」场景。
（**注**：D1 的具体免费额度本次未核实，实施前需查证。）
❌ **不推荐 Workers + KV**：最终一致与现有回读校验逻辑冲突，会引入「验证误判 → 重复推送」。

### 明确排除
- **jsonbin**：一次性额度 + 100KB，问题根源
- **Firebase**：Google 服务，国内基本不可用
- **Supabase**：额度虽好，但「闲置 1 周暂停」对偶尔才开一次的应用是硬伤（放假回来发现同步全挂，还得手动去后台恢复）

## 四、迁移改造清单（已核对到行）

### 4.1 功能核心：只需改 2 个函数 ✅

| 位置 | 作用 | 改动 |
|---|---|---|
| `fetchCloudRecord()` **L10382** | 拉取 | 换 URL / 鉴权头 / 响应解析 |
| `cloudSync()` 推送块 **L10672** | 推送 | `PUT` → 目标服务的写命令 |
| 回读验证 **L10686** | 复用 `fetchCloudRecord()` | **无需改动** |

**❗好消息：负载格式完全不用动。** `{schemaVersion, syncedAt, events, snapshot, barcodeCache}` 这套结构
是**与后端无关**的，直接作为字符串存取即可。`gzip + base64` 那层当初是为绕开 jsonbin 的 100KB 而加，
换到 Upstash / EdgeOne KV 后：
- **保留** → 零改动，还能省流量（推荐先保留，减少变量）
- **去掉** → 可简化代码、便于人工查看云端数据（可作为后续优化）

### 4.2 配置与文案：约 13 处（机械改动）

| 位置 | 内容 |
|---|---|
| L2416 / L2420-2421 | 设置页输入框 `placeholder="jsonbin.io API Key"` 与 `Bin ID` 标签 |
| L4318 | `settings.cloudApiKey` / `cloudBinId` 字段定义 |
| L6247 / L9429 / L10094 / L10893 | 4 处「是否已配置」判断 |
| L9005-9006 / L9386 / L9549-9550 | 配置码生成与解析（扫码接入同一后端） |
| L3248 / L3379 / L3385 | 使用指南正文里的 jsonbin 说明 |
| L9429 | toast 文案「先填写并保存 API Key 与 Bin ID」 |

> 建议：**保留 `cloudApiKey` / `cloudBinId` 两个字段名**，只改语义（当作「令牌」和「端点/键名」），
> 这样配置码、判断逻辑、云同步 schema 全都不用动，迁移面最小。
> ⚠️ L5334 的 changelog 历史条目提到 jsonbin，属**历史记录不改写**。

### 4.3 安全提醒
现状是**密钥存在前端**（本机 localStorage，且随配置码/云同步传递）。换后端时请注意：
- 优先使用**权限受限的令牌**（Upstash 支持 read-only / read-write token；只用 read-write 且限定该库）
- **绝不要**把账号级管理令牌写进前端（如 Cloudflare 账户 API Token）——这正是若选 Cloudflare 必须加 Worker 的原因
- EdgeOne 方案里，边缘函数应校验一个共享密钥，避免端点被任意读写

## 五、建议的推进顺序

1. **先实测 Upstash 的浏览器直连（CORS）**——这是首选方案唯一的未验证项
   （若不通 → 直接走 EdgeOne Makers 方案，反正你本来就用它部署）
2. 实测通过后，改 4.1 的 2 个函数 + 4.2 的文案，**保留负载格式与字段名**，把改动面压到最小
3. **迁移时先做数据搬运**：本地数据不动，把云端那份导出后按新格式写入新后端
   （`schemaVersion` 保持 2/3 不变，新后端第一次拉取即可无缝收敛）
4. 加一层**降级保护**：若新后端也失败，顶栏给出明确文案（顺带把 §403/522 的错误分支一起补上）
