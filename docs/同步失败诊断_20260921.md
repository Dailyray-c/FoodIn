# 云同步频繁失败 · 诊断报告

**日期**：2026-09-21
**版本**：CURRENT_VERSION 2.34.13 / SW v118
**现象**：用户反馈「今天同步功能频繁失败」
**方法**：静态读码 + 用 Playwright 拦截 `api.jsonbin.io` 模拟云端，实测请求消耗与失败时的用户可见提示。**全程未使用用户真实密钥**。

---

## ⚠️ 更正（2026-09-21 20:28）：主因是 jsonbin 源站宕机，不是配额

用户补充「访问 jsonbin 官方站提示 **522**」后，直接复测 API 端点，拿到权威证据：

```
GET https://api.jsonbin.io/v3/b/…/latest
HTTP 522  error_code: 522  error_name: connection_timeout  error_category: origin
ray_id: a3e911767a5b69a4      timestamp: 2026-09-21T12:28:30Z
owner_action_required: true   retryable: true   retry_after: 120
```

**"Cloudflare could not establish a TCP connection to the origin server."**

→ **522 = Cloudflare 边缘连不上 jsonbin 的源站**。这是**服务端故障**，
`owner_action_required: true` 表示需由 jsonbin 修复，**与用户的密钥、额度、数据量、代码全部无关**。

**因此本报告下方「一、结论」中列为第 1 位的「配额用尽」不是今天的原因。**
那一节保留作为**潜在风险**记录（其代码缺陷部分仍然成立），但**今天不需要照它处置**。

> 教训：我最初把「额度用尽」排在第一，依据是「耗时 44 天 ≈ 额度寿命 44 天」的时间巧合 ——
> **这是相关性推断，不是证据**。真正的证据是 HTTP 状态码 + 响应体。
> 拿到 522 这个硬信号后，结论立刻收敛。**先要硬信号，再谈原因。**

## 一、结论（**已被上方更正**，此处保留原始推理供对照）

| 排序 | 原因 | 可能性 | 判据 |
|---|---|---|---|
| **1** | **jsonbin 免费额度用尽 → HTTP 403「Requests exhausted」** | **高** | 免费版 10,000 请求**一次性**不刷新；本项目每次同步实测消耗 **3 次**；按日均消耗倒推，时间点与「第 44 天」高度吻合 |
| 2 | 负载逼近免费版 **100KB** 单 Bin 上限 → HTTP 413 | 中 | 实测 1000 商品 + 5000 流水 → gzip 后 **93.9KB**，余量仅 6% |
| 3 | 网络抖动 / 15 秒超时 | 低 | 代码有 15s 超时与退避重试，且重试成功后正确复位，无失控迹象 |
| 4 | 密钥失效（401） | 低 | 有专属文案「API Key 无效或已过期」，与「频繁失败」描述不符（除非用户看到的正是这句） |

> ⚠️ **已排除的错误线索**：我在本机 curl `api.jsonbin.io` 返回 `http_code=000`（连接失败），
> 但同一时刻 `example.com` 正常、`api.github.com` 也失败 —— 说明是**本机出网白名单拦截**，
> **不能据此判断 jsonbin 宕机**。这是「断言写错 ≠ 产品有 Bug」的典型案例。

## 二、主因论证：免费额度是「一次性」的

jsonbin 官方两处文档明确：

- 定价页 FAQ：*「The requests which are credited when you are on a Free Trial… are credited **only for once**.
  If you need additional requests then you need to purchase them separately.」*
- 支持页：*「we provide 10,000 requests to get started with, for a Free Trial account.
  These requests are **only for once, and will not be credited** unless you purchase additional requests.」*
- 错误参考（Read Bins API）：*「Requests exhausted. Buy additional requests at https://jsonbin.io/pricing」*，
  归类在 **400 / 401 / 403 / 404** 之中 → 实际返回 **HTTP 403**。

**关键点：10,000 次不是「每月 10,000」，而是账户终身一次性额度。用完即永久 403。**

### 2.1 本项目的额度消耗模型（实测）

用 `page.route` 拦截 `api.jsonbin.io` 做成「有状态 echo 云端」，统计每次同步的真实请求数：

| 场景 | 实测请求数 | 明细 |
|---|---|---|
| 首次同步（云端学习本地数据） | **3** | `GET → PUT → GET` |
| **稳态：无任何变更** | **1** | `GET`（仅拉取） |
| **稳态：一次真实变更** | **3** | `GET`（拉取）→ `PUT`（推送）→ `GET`（回读验证） |
| 连续 10 次变更（15s 防抖合并） | **3** | 防抖有效，10 次变更合并为 1 次同步 |

**核心事实：每个「变更批次」固定消耗 3 次请求，其中 1 次是回读验证（占 33%）。**

### 2.2 触发频率（谁会调用同步）

| 触发点 | 位置 | 条件 |
|---|---|---|
| 任何本地变更后 15 秒 | `saveData()` L6250 | 真有防抖（`clearTimeout` 合并），连续操作只算 1 次 |
| 回到前台 | `visibilitychange` L10908 | 距上次同步 ≥ 2 分钟 |
| 断网恢复 | `online` L10904 | 1 秒防抖 |
| 启动时 | L10893 | 有待推事件，或距上次 ≥ 10 分钟 |
| 自动保存 | `setupAutoSave()` L10095 | 仅当 `autoSaveInterval > 0`（**默认 0，未启用**） |
| 失败重试 | `scheduleSyncRetry()` L10464 | 30s→60s→…→**5 分钟封顶**，成功后复位 |

### 2.3 天数倒推（与「今天」吻合）

- 假设日均 60 个变更批次（录入/入库/编辑/撤销等）→ 60 × 3 = **180 次/天**
- 10,000 ÷ 180 ≈ **55 天**
- 项目起始 2026-08-08 → 今天 2026-09-21 = **44 天**
- 若日均约 **75 个批次**（75×3 = 225/天），10,000 ÷ 225 ≈ **44 天** —— **恰好今天耗尽**

一旦耗尽，此后**每一次**同步都被 403 拒绝，表现为「频繁失败」甚至「全部失败」。

### 2.4 更糟的是：用户看不出是配额问题

代码只对 **401 / 413** 做了专门文案，**403 与 429 没有分支**：

```js
// L10389（拉取失败）
const reason = res.status === 401 ? 'API Key 无效或已过期' : ('HTTP ' + res.status);
// L10703-10705（推送失败）
if (put.status === 401) toastErr('云同步', 'API Key 无效或已过期');
else if (put.status === 413) toastErr('云同步', '数据超出 jsonbin 单 Bin 容量');
else toastErr('云同步', 'HTTP ' + put.status);
```

**已复现的 403 实际表现**（模拟 `403 + {"message":"Requests exhausted…"}`）：

| 位置 | 显示内容 |
|---|---|
| 顶栏状态灯 | **`同步失败`**（error 态，`holdMs=0` → **常驻不消失**） |
| 设置页 `cloudSyncStatus` | `同步失败：HTTP 403（已中止，未覆盖云端）` |
| 控制台 | `Failed to load resource: the server responded with a status of 403 (Forbidden)` |

→ 用户看到「同步失败 / HTTP 403」，**无法得知是配额用尽**，也不会想到要去 jsonbin 后台充值。这是本次最该修的部分。

## 三、次因论证：负载逼近 100KB 上限

免费版单 Bin 上限 **100KB**（Pro 才到 10MB）。实测 gzip + base64 后的 PUT 负载（即实际占用的 Bin 大小）：

| 数据量 | PUT 负载 | 占比 |
|---|---|---|
| 30 商品 + 60 流水 | 2.7 KB | 3% |
| 200 商品 + 500 流水 | 11.9 KB | 12% |
| 500 商品 + 2000 流水 | 40.3 KB | 40% |
| **1000 商品 + 5000 流水** | **93.9 KB** | **94%** ⚠️ |

- 一旦越界 → HTTP 413，代码有专门文案「数据超出 jsonbin 单 Bin 容量」（这个提示是清楚的）
- ⚠️ **`snapshot.knownIds` 只增不减**（删除墓碑永久保留，见 v2.18.0 注释），
  随使用时长**单调增长**，是体积膨胀的主要长期来源
- gzip 已把体积压到原来的约 1/5；若浏览器不支持 `CompressionStream` 会回退未压缩 v2 结构 → 体积暴增 5 倍，**必然 413**

## 四、如何确认（请用户做，1 分钟）

1. **看错误文案**（最能一锤定音）：
   | 看到 | 结论 |
   |---|---|
   | `同步失败：HTTP 403` | **配额用尽**（主因） |
   | `同步失败：密钥无效` | 401，密钥问题 |
   | `同步失败：数据超限` | 413，负载超 100KB |
   | 只有 `同步失败` | 403 / 429 / 网络 |
2. **F12 → Network → 过滤 `jsonbin`** → 点开红色那条 → Response：
   若报文含 `Requests exhausted` → **确认是配额用尽**。
3. **登录 jsonbin.io → 查看请求配额余量**（API Keys / 账户页）。

## 五、修复建议（待确认后实施）

### A. 立即止血（不改代码）
- jsonbin 后台购买 Additional Requests，或升级 Pro（100,000 次 + 10MB/Bin）
- 或更换存储后端（自建 / 其他服务）

### B. 代码层：把 403/429 变成可理解的提示（**推荐，低风险**）
在 `fetchCloudRecord` 与推送失败分支补 403 分支，读响应体识别 `Requests exhausted`：

| 状态码 | 建议文案 |
|---|---|
| 403（报文含 `exhausted`） | 「云同步请求额度已用尽，请到 jsonbin 提升额度」 |
| 429 | 「同步过于频繁被限流，稍后自动重试」 |
| 其他 4xx | 保留 `HTTP xxx` |

顺带把 403 的顶栏文案从通用「同步失败」改为「同步失败：额度用尽」，并**停止无意义重试**
（配额用尽时重试再多也不会成功，且重试本身也在消耗/触发请求）。

### C. 代码层：降低请求消耗（**收益最大**）
当前每个变更批次 3 次请求，可优化：

| 手段 | 节省 | 风险 |
|---|---|---|
| **回读验证改为按条件执行**（如每 N 次推送才验证一次，或仅在上次推送未确认时才验证） | **33%** | 中：需确认「部分确认」逻辑仍安全 |
| 变更批次合并窗口 15s → 30s（密集录入场景） | 视场景 | 低：仅影响同步延迟 |
| 回前台拉取阈值 2 分钟 → 5 分钟 | 视场景 | 低：仅影响多设备实时性 |
| `knownIds` 加体积上限 / 定期压缩 | 防 413 | 中：需保证删除墓碑语义不被破坏 |

> 粗算：仅「条件化回读验证」一项，就能把 10,000 额度的寿命从约 44 天延长到约 **66 天**。

### D. 长期：换掉 jsonbin 免费版
一次性质度 + 100KB 上限，本质上不适合作为长期数据后端。可考虑：
自建轻量后端、Cloudflare KV/R2、Supabase、或其他有「按月刷新」额度的服务。

## 七、jsonbin 源站宕机（522）专项

### 7.1 「首页能打开」是假象
`jsonbin.io` 首页此时仍可正常加载（Cloudflare 缓存了静态页），但 `api.jsonbin.io` 返回 522。
**判断服务是否可用，必须打 API 端点，不能看官网首页。**

### 7.2 故障期间的数据安全性（已实测，全部通过 ✅）

模拟 `522`（返回 Cloudflare 的真实 HTML 报文）后核对：

| 核对项 | 结果 |
|---|---|
| 是否向云端发起 PUT | **0 次** → 云端数据未被覆盖 ✅ |
| 本地商品（内存 / localStorage） | 完好 ✅ |
| 待推事件（内存） | 保留 ✅ |
| 待推事件（`food_inventory_sync_v2` 持久化） | **保留** → 关页面/刷新也不丢 ✅ |

**为什么云端安全**：`cloudSync` 的设计是「**先拉取，拉不到就绝不下发**」——
拉取失败时在 `L10487` 直接 `return { ok: false }`，**根本走不到推送分支**。
这条铁律在本次故障中起了关键作用（若反过来先推后拉，宕机期间的半截数据会覆盖云端）。

**恢复机制**：
- 待推事件在本地累积并持久化，服务恢复后自动补推
- 失败退避重试 30s → 60s → … → **5 分钟封顶**（成功后复位）
- 断网恢复（`online` 事件）与回到前台（≥2 分钟）也会触发补同步

→ **结论：什么都不用做，等 jsonbin 修好即可，数据会在恢复后自动补齐。**

### 7.3 用户可见提示
- 顶栏：`同步失败`（error 态 `holdMs=0` → **常驻不消失**，符合「让用户看见」的设计意图）
- 设置页：`同步失败：HTTP 522（已中止，未覆盖云端）`
- 控制台：`Failed to load resource: the server responded with a status of 522`

**可改进**：522/521/523/524 属 Cloudflare 起源错误，文案可改为
「云端服务暂时不可用（522），本地数据已保留，将自动重试」，让用户不必担心数据丢失。

### 7.4 应对建议

| 时间尺度 | 动作 |
|---|---|
| **现在** | 不用操作。本地照常录入，数据不会丢；服务恢复后自动补齐 |
| 几小时内 | 若持续 522，可同时关注 jsonbin 官方渠道；必要时联系其客服 |
| 若长时间不可用 | 考虑换后端（见 §五 D）。本次宕机正好说明**单点依赖第三方免费服务**的风险 |
| 故障恢复后 | 建议核对一次云端数据是否与本地一致（首次同步会自动收敛） |

**❗注意**：不要在故障期间反复手动点同步——排查不了问题，只会在服务恢复瞬间堆积并发请求。
